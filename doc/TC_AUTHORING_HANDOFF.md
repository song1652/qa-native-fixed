# TC Authoring Studio 개발 인수인계

> **독자**: TC 스튜디오 기능을 구현할 개발 에이전트(LLM)와 그 작업을 맡기는 사람.
> 이 문서 하나로 "무엇을, 어떤 순서로 읽고, 어떻게 진행하고, 언제 멈추고, 무엇을 보고하는지"를 알 수 있게 썼다.
> 작성: 2026-09-30 · 구현 상태: **아직 코드 없음** (계획만 있음. 모든 계획 코드는 저장소 사본에서 실행까지 검증됨)

---

## 1. 무엇을 만드나 (30초 요약)

QA 대시보드에 **"TC 스튜디오"** 화면을 추가한다.

1. 회사 엑셀 Full TC(야핏무브 양식)를 웹으로 가져와 보고 고치고, 같은 양식의 엑셀로 다시 내보낸다 — **Phase 1**
2. PRD 파일·붙여넣은 기획을 넣으면 로컬 `claude` CLI(도구 없이 실행)가 그 양식대로 TC 초안을 쓰고, 사람이 원문을 옆에 두고 승인·반려·재생성한다 — **Phase 2**
3. Confluence·Figma·PRD URL에서도 가져오고, 출처 문서가 바뀌면 관련 케이스를 "재검토 필요"로 표시한다 — **Phase 3**
4. 웹으로 자동화할 수 있는 케이스를 기존 Playwright 파이프라인용 `testcases/*.md`로 내보낸다 — **Phase 4**

외부 LLM API·SDK는 쓰지 않는다. 생성은 이 PC에 로그인된 `claude` CLI를 헤드리스로 부르는 방식이다.

## 3. 시작 전 준비

```bash
cd <저장소>
git status                       # 깨끗한지 확인. 작업은 새 브랜치에서: git switch -c feat/tc-studio-phase1
.venv/bin/python -m pytest -q    # 기준선: 677 passed, 1 skipped
.venv/bin/python -m playwright install chromium   # E2E용 (이미 있으면 바로 끝난다)
```

- 파이썬은 항상 `.venv/bin/python`을 쓴다 (Python 3.14, openpyxl 3.1.x).
- **Phase 2부터**: `claude` CLI가 PATH에 있고 로그인돼 있어야 실제 생성이 된다. 테스트는 가짜 CLI를 쓰므로 없어도 통과한다. G2에서 `pypdf`, `python-docx`를 설치한다.
- **cmux 터미널 주의**: `node`·`npm`·`claude`가 `Cannot find module …/restore-node-options.cjs`로 죽으면 `NODE_OPTIONS`가 사라진 임시 파일을 가리키는 것이다. 명령 앞에 `env -u NODE_OPTIONS`를 붙이거나 터미널을 새로 연다. (생성 실행기는 자식 프로세스에서 `NODE_OPTIONS`를 빼고 실행하도록 이미 계획돼 있다.)
- 실제 데이터 `~/Downloads/야핏무브_Full.xlsx`는 저장소에 넣지 않는다. 테스트는 `tc_fixtures.build_template_workbook()`이 만든 가짜 워크북을 쓴다. 실제 파일은 계획의 "수동 확인" 단계에서만 쓴다.

## 4. 작업 1개를 진행하는 방법 (모든 작업 공통)

계획의 각 작업은 `- [ ]` 체크박스 단계로 되어 있다. **위에서부터 그대로** 진행한다.

1. **작업 절 전체를 먼저 읽는다** — Files(만들고 고칠 파일), Interfaces(앞 작업에서 받는 것·뒤 작업에 넘기는 것), 단계.
2. **실패하는 테스트부터** 파일에 쓰고 실행해서 계획이 적은 이유로 **실패하는지** 확인한다. 이 단계를 건너뛰지 않는다. 다른 이유로 실패하면 멈추고 원인을 찾는다.
3. **구현**: 계획의 코드 블록을 그대로 넣는다.
   - ` ```python ` / ` ```javascript ` 블록 = 파일 전체 또는 계획이 말한 위치에 추가할 내용
   - ` ```diff ` 블록 = 기존 파일에 적용할 변경 (`-` 줄이 지금 파일에 있어야 한다). `git apply`가 줄 번호 때문에 실패하면 `-`/`+` 줄의 **문맥 텍스트로 위치를 찾아** 손으로 적용한다.
   - "N행 아래에 추가" 같은 줄 번호는 참고용이다. 파일이 이미 바뀌어 번호가 어긋나면 함께 적힌 **기준 텍스트**(예: "`IMPORT_PROFILES_PATH = …` 줄 아래")로 찾는다.
4. **통과 확인**: 계획의 `Run:` 명령을 그대로 실행하고 `Expected:`와 개수까지 비교한다. Phase 중간의 "회귀" 명령(전체 테스트)도 빠뜨리지 않는다.
5. **커밋**: 계획의 `git add` 목록과 커밋 메시지를 쓴다. 커밋 메시지 끝에 저장소 규칙의 `Co-Authored-By` 줄을 붙인다. **push는 사람이 요청할 때만** 한다.
6. 다음 작업으로.

### 해도 되는 것 / 하면 안 되는 것

- ✅ 계획 코드를 그대로 쓰기 — 검증된 코드다. "더 좋게" 고치고 싶어도 먼저 그대로 넣고 통과시킨다. 개선은 별도 커밋으로, 테스트가 통과하는 상태를 유지하면서.
- ✅ 계획에 없는 작은 수정이 꼭 필요하면(예: 저장소가 계획 작성 뒤 바뀜) 최소한으로 하고 커밋 메시지와 보고에 적는다.
- ❌ 실패하는 테스트를 통과시키려고 **테스트를 약하게 고치기**(기대값을 실제 결과에 맞추기, `skip`, 검사 줄 삭제). 기대값이 틀렸다고 판단되면 이유를 보고한다.
- ❌ 다음 Phase 코드를 미리 넣기, 작업 여러 개를 한 커밋에 묶기.
- ❌ `claude -p … --dangerously-skip-permissions` (생성 세션은 `--restricted --tools ""`만), 외부 LLM SDK·API 키, 원본 xlsx 덮어쓰기, `state/pipeline.json` 수동 수정, 토큰을 화면·로그·커밋에 남기기.
- ❌ 목업(`design-previews/tc-authoring-studio.html`)을 구현 파일처럼 고치기. 목업은 디자인 기준이다. `static/css/tc-studio.css`는 W1의 생성 스크립트로만 만든다(직접 고치지 않는다).

## 5. 막혔을 때

| 상황 | 할 일 |
|---|---|
| diff의 `-` 줄이 파일에 없다 | 앞 작업을 빠뜨렸거나 순서가 틀린 것이다. `git log`로 앞 작업 커밋을 확인한다. 저장소가 계획 뒤에 바뀐 것이면 의미가 같은 위치에 적용하고 보고한다 |
| 계획 코드를 넣었는데 테스트가 실패 | 오류 메시지와 테스트를 읽고 **원인을 먼저 찾는다**(추측으로 고치지 않는다). 환경 차이(패키지 버전, 경로, 브라우저)인지 코드 문제인지 가른다. 고치면 [`agents/lessons_learned.md`](../agents/lessons_learned.md)에 한 줄 기록 |
| E2E가 가끔만 실패 | 같은 테스트를 단독으로 5번 돌려 본다. 단독에서 매번 통과하고 전체 실행 때만 가끔 실패하면 부하로 보고(대기 시간은 이미 10초로 늘려 둠). 단독에서도 실패하면 결함이다 |
| 실제 Confluence·Figma 응답이 녹화본과 다름 (Phase 3 W11) | 실제 응답 모양으로 `connector_fixtures.py`를 먼저 고치고, 테스트가 실패하는 것을 본 뒤 코드를 고친다 |
| 계획과 PRD·명세가 다름 | 계획을 따른다 (2장 우선순위) |
| 30분 넘게 같은 문제 | 멈추고 사람에게 보고한다 (7장 형식) |

## 6. Phase 완료 기준

각 Phase 계획 마지막 작업(W4·W8·W11·W13)에 완료 확인 절차가 있다. 공통 기준:

- `tests/unit/tc_library` 전부 통과 + 전체 테스트 통과(기준선 677 + 누적 TC 스튜디오 테스트, 1 skipped). 누적: Phase 1 → 717, Phase 2 → 754, Phase 3 → 776, Phase 4 → **790 passed**
- 계획의 "수동 확인" 단계 수행 (Phase 1: 실제 엑셀 926건 왕복 / Phase 2: 실제 `claude`로 생성 / Phase 3: 실제 계정 / Phase 4: 실제 파이프라인 실행)
- 로드맵 표의 해당 Phase에 `✅ 완료 (날짜)` 표시
- Phase가 끝나면 **멈추고 보고**한다. 사람이 확인한 뒤 다음 Phase로 간다.

## 8. 알려진 한계 (계획 작성 시점)

- **실제 Confluence·Figma 계정으로는 검증하지 않았다.** 녹화 응답으로만 테스트했다. Phase 3 W11에서 확인한다.
- 생성은 실제 `claude` CLI(haiku)로 1회만 확인했다(초안 5건, 한국어 유지, 인용 일치, $0.08, 약 2분). 기본 모델·큰 문서에서의 품질·시간은 Phase 2 W8에서 확인한다.
- E2E는 전체 실행 중 부하로 드물게 시간 초과가 났다(20회 중 1회). 기본 대기 시간을 10초로 늘린 뒤 전체 3회 연속 통과했다.
- 목업의 버그 하나(`.chip-select.empty`가 빈 화면 `.empty`와 충돌)는 구현에서 `is-unset` 클래스로 피했다. 목업 자체는 고치지 않았다.
- 모바일 앱 TC 중 웹으로 자동화할 수 있는 케이스는 적어서, Phase 4 md 내보내기는 소수 케이스에만 쓰인다.

## 9. 다른 LLM에게 줄 시작 프롬프트 (복사해서 쓰기)

```
너는 qa-native-fixed 저장소에서 "TC Authoring Studio" 기능을 구현하는 개발자다.

1. doc/TC_AUTHORING_HANDOFF.md를 끝까지 읽고 그 절차를 따른다.
2. CLAUDE.md의 "행동 원칙"과 "절대 규칙"을 읽는다.
3. doc/TC_AUTHORING_ROADMAP.md를 읽는다.
4. 이번에는 Phase {N}만 한다: doc/plans/{Phase N 계획 파일}의 작업을 {첫 작업 ID}부터 순서대로 진행한다.
   - 각 작업은 "실패하는 테스트 → 실패 확인 → 계획 코드 적용 → 통과 확인 → 커밋" 순서를 지킨다.
   - 계획의 코드는 검증된 코드다. 그대로 쓰고, 테스트를 약하게 고치지 않는다.
   - 계획과 다르게 해야 하면 이유를 커밋 메시지와 보고에 적는다.
5. 브랜치 feat/tc-studio-phase{N}에서 작업하고, push는 하지 않는다.
6. Phase {N}의 마지막 작업까지 끝나면 멈추고 HANDOFF 7장 형식으로 보고한다.
   막히면(같은 문제 30분 이상, 판단이 필요한 차이) 그 자리에서 멈추고 보고한다.
```

Claude Code가 아닌 LLM이면 계획 머리말의 "REQUIRED SUB-SKILL: superpowers:…" 줄은 무시해도 된다. 체크박스 단계만 따르면 된다.
